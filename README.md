# Simulated Well Sensor

A real-time streaming data engineering project that simulates oil and gas well sensor telemetry, publishes the data to Apache Kafka, consumes and processes the stream with Apache Spark Structured Streaming, and performs event-time windowed analytics.

## Project Overview

The project simulates telemetry generated by an oil and gas production well and builds a streaming pipeline capable of processing the data in near real time.

The simulated sensor produces measurements including:

- Pressure (psi)
- Temperature (°C)
- Flow rate (bpd)
- Vibration (mm/s)

The telemetry is serialized as JSON and published to an Apache Kafka topic. Apache Spark Structured Streaming consumes the Kafka stream, parses the telemetry against a defined schema, applies event-time processing and watermarks, and calculates windowed statistics for each well.

## Simulated Telemetry

Each generated reading contains:

```json
{
  "well_id": "WELL-001",
  "timestamp": "2026-10-13T05:54:18.473860+00:00",
  "pressure_psi": 2801.05,
  "temperature_c": 80.63,
  "flow_rate_bpd": 1252.34,
  "vibration_mms": 0.701
}
```

The producer generates a new reading every 2 seconds.

The simulated sensor values are generated within the following ranges:

| Parameter | Range |
|---|---:|
| Pressure | 2800–2900 psi |
| Temperature | 75–82 °C |
| Flow rate | 1150–1350 bpd |
| Vibration | 0.2–0.8 mm/s |

## Kafka Producer

The Python producer:

1. Generates simulated sensor readings.
2. Adds a UTC timestamp.
3. Serializes each reading to JSON.
4. Uses `well_id` as the Kafka message key.
5. Publishes the telemetry to `well-telemetry`.
6. Logs Kafka partition and offset information.
7. Continues publishing every 2 seconds.

Example log information includes:

```text
Sent telemetry | partition=0 | offset=... |
pressure=... psi | temperature=... °C |
flow=... bpd | vibration=... mm/s
```

## Kafka Consumer

A Python Kafka consumer is included to independently verify Kafka message consumption.

The consumer:

- Connects to `localhost:9092`
- Subscribes to `well-telemetry`
- Uses consumer group `well-sensor-consumer`
- Starts from the earliest available offset when appropriate
- Deserializes JSON telemetry
- Logs received sensor readings
- Handles malformed telemetry and Kafka errors

The consumer provides a simple way to validate the Kafka layer independently from Spark.

## Spark Structured Streaming

Spark consumes the Kafka topic using the Spark Kafka connector:

```text
org.apache.spark:spark-sql-kafka-0-10_2.13:4.2.0
```

The streaming job performs the following operations:

1. Reads the Kafka stream.
2. Extracts the Kafka message value.
3. Converts the JSON payload into a structured DataFrame.
4. Applies an explicit telemetry schema.
5. Uses the telemetry timestamp as event time.
6. Applies a 10-second watermark.
7. Groups records into 10-second windows by `well_id`.
8. Calculates average sensor values.
9. Counts the number of readings in each window.
10. Writes the aggregated results to the console.

## Telemetry Schema

Spark applies the following schema:

```text
well_id          STRING
timestamp        TIMESTAMP
pressure_psi     DOUBLE
temperature_c    DOUBLE
flow_rate_bpd    DOUBLE
vibration_mms    DOUBLE
```

Using an explicit schema ensures that the incoming JSON telemetry is converted into correctly typed Spark columns.

## Event-Time Processing

The Spark job uses the telemetry timestamp rather than processing time for window calculations.

A 10-second watermark is applied to allow limited out-of-order data while controlling the amount of streaming state maintained by Spark.

The aggregation uses 10-second tumbling windows:

```text
Window 1: 07:36:10 → 07:36:20
Window 2: 07:36:20 → 07:36:30
Window 3: 07:36:30 → 07:36:40
...
```

## Windowed Analytics

For every well and 10-second window, the pipeline calculates:

| Metric | Description |
|---|---|
| `avg_pressure_psi` | Average pressure |
| `avg_temperature_c` | Average temperature |
| `avg_flow_rate_bpd` | Average flow rate |
| `avg_vibration_mms` | Average vibration |
| `reading_count` | Number of readings in the window |

Example output:

```text
WELL-001
2026-10-13 07:36:10
2026-10-13 07:36:20
avg_pressure_psi     = 2837.388
avg_temperature_c    = 79.852
avg_flow_rate_bpd    = 1230.018
avg_vibration_mms    = 0.563
reading_count        = 5
```

## Checkpointing

Spark Structured Streaming uses checkpointing to maintain streaming query state and progress.

The project uses:

```text
checkpoints/windowed_analytics_v2
```

Checkpoint directories are excluded from Git because they contain runtime state rather than source code.

The project also avoids committing generated log files and Python cache directories.

## Docker

Kafka is containerized using Docker Compose.

Start Kafka with:

```bash
docker compose up -d
```

Check the container:

```bash
docker compose ps
```

Expected service:

```text
well-sensor-kafka
```

Stop the service without deleting its persistent data:

```bash
docker compose stop
```

Restart Kafka:

```bash
docker compose restart kafka
```

Do not use the following command if Kafka data needs to be preserved:

```bash
docker compose down -v
```

The `-v` option removes the Docker volume containing Kafka data.
